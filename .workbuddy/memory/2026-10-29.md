## 报名防超卖改造（signup.lua 重构）—— 已落地并压测通过

### 问题
`signup.lua` 把 Redis 当成名额的唯一真相：
1. `if (not stock) then set(stockey, quota)` —— key 丢失就按**总名额**重置，50 人活动能超卖到 100 人；
2. 脚本内 `incrby -1` 先扣，Java 再写 `tb_signup`，跨库无事务，断在中间就是「幽灵报名」（Redis 扣了、DB 没记录，用户既报不上也取消不了）；
3. `cancel_signup.lua` 补位时不校验对方是否还在候补状态，能把已取消的人复活。

### 决策过程（用户主导，最终方案）
- 讨论过「行锁 + count」：不加字段也能 100% 正确，但受 **RR 快照读**影响（事务第一条 `selectById` 就固定了快照，之后 count 读到旧值照样超卖），且要求 `cancel` 等所有写路径都遵守锁协议，漏一处就破。
- 最终选 **DB 余量字段 + 条件更新**：一条 `UPDATE ... WHERE remain_quota > 0` 同时完成判断和扣减，是当前读、不受快照影响，Redis 彻底降级为挡流。

### 改动清单
- `database/10_activity_remain_quota.sql`：`tb_activity` 加 `remain_quota INT NOT NULL DEFAULT 0`，按 `count(status=1)` 回填。
- `Activity.java`：加 `remainQuota` 字段；`quota` 语义固定为总名额（只写一次）。
- `ActivityMapper`：新增 `takeQuota`（`remain_quota>0` 才 -1，返回 0 = 满）、`giveBackQuota`（+1 且不超过 quota）、`selectRemainQuota`。
- `signup.lua` 重写：**只读不写**，返回 0 继续 / 1 满 / 2 重复 / 3 缓存未就绪，不再 `SET`、不再 `DECR`。
- `cancel_signup.lua`：删掉 `incrby stockey`，KEYS 从 `[stock, users, waitlist]` 改为 `[users, waitlist]`，名额增减交给 DB。
- `SignupServiceImpl.signup()`：加 `@Transactional`；流程改为 挡流 → `takeQuota` 裁决 → 写明细（同事务，失败自动回滚名额）→ 回写 Redis（失败只记日志）。
- `SignupServiceImpl.tryGate()`：缓存缺失时 `syncStockFromDb` 重建再问一次；仍失败 / Redis 抛异常 → 返回 `GATE_UNAVAILABLE`，接口报「服务器繁忙」（按用户要求，不偷偷放行）；带 5 秒冷却避免每个请求等连接超时。
- `SignupServiceImpl.cancel()`：DB 归还名额；补位加 `.eq(status, 2)` 防复活；结束后 `DEL stock` 让下次从 DB 重建（不用 INCR，避免漂移）。
- `ActivityServiceImpl`：publish 时 `remainQuota = quota` 并初始化 Redis；列表/详情的 `remainingQuota` 直接取 DB，不再问 Redis。

### 验证结果
- 并发压测（`Temp/chdb/race.js`）：12 人抢 5 个名额 → **成功 5、名额已满 7、DB `status=1` 恰好 5 条、`remain_quota=0`**，无超卖。
- 自愈验证（`Temp/chdb/verify2.js`）：手工 `DEL signup:stock:{id}` 后报名，自动从 DB 重建为正确余量并继续扣减；取消后名额归还、key 被删待重建；详情页 `remainingQuota` 与 DB 一致。全部通过。

### 尚未处理（下一轮）

## 候补链路：入队失败的回滚 + 排位显示 0（已修，档一）

### 决策背景
用户选择「档一」（最小改动）而非「档二」（加 `queue_time` 落库 + 删 Redis List）。理由：15:00 收工，档二需 40 分钟；顺序错乱的根治留待以后。

### 关键认知（用户提出「加事务没啥用」，已澄清）
- 候补是「DB 先写、Redis 后写」，方向与报名相反 → **Redis 失败只能靠事务回滚 DB**，不能靠补偿。
- 若 try-catch 只吞异常：库里留 `status=2`、队列里没他 → 用户重试命中「已报名或已在候补中」→ **永久卡死**。
- 正确做法：`@Transactional(rollbackFor = Exception.class)` + **抛** `BizException(500,"服务器繁忙")`。
- `@Transactional` 在此不失效（Controller → Service 跨 Bean 调用，非自调用）。

### 改动
- `SignupServiceImpl.joinWaitlist`：加 `@Transactional`；`rightPush` 包 try-catch，失败 `log.error` + 抛「服务器繁忙，请稍后重试」触发回滚。
- `SignupServiceImpl.queryMine`：`indexOf` 返回 `-1` 时不再 `+1` 变成「第 0 位」（`range >= 0` 才设排位）；Redis 异常包 try-catch，排位查询失败不影响「我的报名」列表返回。

### 验证（`Temp/chdb/verify3.js`，16 项全过）
- 正常候补：队列长度 1、`status=2`、`waitPosition=1`。
- 队列丢人：`lrem` 后 mine 仍 200，`waitPosition` 为 `null`（旧代码是 0）。
- **回滚验证**：把 `signup:waitlist:{id}` 用 `SET` 改成 string 制造 WRONGTYPE → 新用户候补返回 500「繁忙」，DB **0 行**（插入已回滚）；已取消用户复活分支同样回滚为 `status=3`（未变 2）。
- 恢复 key 后候补正常，排位 1。测试数据与缓存键已全部清理（`tb_activity` 回到 30001=80/80、30002=120/120）。

### 仍遗留
- 候补**顺序**仍只在 Redis List（用户已知，决定暂不处理）；`cancel()` 里 `lrem`/`rightPush` 补偿仍可能失败；`execute(cancelSignupScript)` 在 try 外，Redis 挂时取消接口报全局 500（无副作用，可重试）。

   - 新增 `@Slf4j` + `forbidden()`，日志记录来源 IP
5. 8 个服务 `application.yml` 加 `campus.internal.token: ${INTERNAL_TOKEN:dev-internal-token}`
   - user-service 额外 `protected-paths: /users/*/balance/deduct`
